VICEHUB · PRIMEIRO DEPLOY

Dia do deploy

A ordem por que isto tem de acontecer, com o que prova que cada passo correu bem. O porquê de cada coisa está no readme, em Pôr em produção — aqui está só a sequência.

0 de 10 feitos
Nenhuma chave passa por uma conversa. As do Stripe, do SMTP, do Turnstile, da Google e do Discord vão do painel de quem as emite para o painel do Railway, e mais lado nenhum. O repositório é público.

  1. A identificação legal, antes de tudo

    apps/web/src/legal/operator.ts tem sete campos vazios, e enquanto estiverem vazios as páginas de termos e de privacidade dizem, em cima e com todas as letras, que não são definitivas. É código: entra num commit, não num painel.

    • a firma, como está registada (não é “ViceHub”)
    • a sede social, com país
    • o NIF ou número de registo comercial
    • o email para estes documentos e para dados
    • a lei aplicável e o foro
    • onde ficam os servidores
    • onde um consumidor reclama fora dos tribunais

    As duas páginas legais deixam de trazer o aviso em cima.

  2. Neon: a base de dados, e os dois endereços

    Criar o projeto e guardar os dois endereços que ele dá. O do pool é o que a API usa; o directo é por onde as migrações correm — num pool em modo de transação elas falham ou ficam penduradas, e sempre a meio de um deploy. 

    DATABASE_URL=o do pool
DIRECT_DATABASE_URL=o directo

    Os dois endereços copiados para onde ninguém mais lhes chega.

  3. Railway: a API

    Apontado a este repositório. O railway.json já diz o resto: compila, corre db:migrate:deploy antes de trocar de versão, arranca, e sonda /api/v1/health/ready. As variáveis são as do .env.example — e o WEB_DIST_PATH fica por definir, que aqui quem serve a interface é o Vercel. 

    openssl rand -hex 48   # JWT_ACCESS_SECRET
openssl rand -hex 48   # JWT_REFRESH_SECRET (diferente)

    Estas, em produção, a API recusa arrancar sem elas: AUTH_COOKIE_SECURE=true, APP_PUBLIC_URL=https://…, SMTP_URL, MAIL_FROM — e TRUST_PROXY, que no Railway é true: sem ela, todos os pedidos chegam com o endereço do proxy e o limite passa a ser da plataforma inteira em vez de ser de cada pessoa. Um número de saltos (1, como no Express) é recusado.

    /api/v1/health/ready responde 200.

  4. O seed, uma vez, contra a base nova

    npm run db:seed

    Sem ele a API recusa arrancar, e diz-o na primeira linha do log: não há cargo base para dar a quem se regista. Num serviço que reinicia sozinho, isto aparece como um processo que não fica de pé.

    21 permissões e 9 cargos garantidos.

  5. Vercel: a interface

    Mesmo repositório, raiz do projeto na raiz do repositório. O vercel.json traz o comando, a pasta de saída e a reescrita que faz um F5 em /crews/alguma-coisa devolver a página em vez de 404. 

    VITE_PUBLIC_URL=https://vicehub.com

    Sem esta, o cartão de um link partilhado e o sitemap.xml saem com o domínio que está escrito no sitio-publico.ts.

    Um F5 numa página interna não dá 404.

  6. Os domínios, e as três linhas que os nomeiam

    Não é acabamento: é o que faz a sessão existir. O refresh token vive num cookie SameSite=strict, que segue de vicehub.com para api.vicehub.com — o mesmo sítio registável — e não segue de …vercel.app para …railway.app. Com os nomes por omissão, o login funciona, o refresh devolve 401, e a sessão morre a cada F5 sem nada no ecrã a explicar porquê. 

    connect-src            vercel.json
CORS_ALLOWED_ORIGINS   Railway
VITE_PUBLIC_URL        Vercel

    Entrar, fechar o separador, voltar: a sessão continua.

  7. Stripe: os quatro preços, o portal, o webhook

    Preços recorrentes mensais, um por plano. Um plano está à venda se, e só se, tiver preço — dá para abrir só o da crew e deixar os escalões de servidor fechados. 

    https://api.vicehub.com/api/v1/billing/webhook

    O segredo do webhook vai para o Railway e para lado nenhum mais.

    A escada de preços mostra botões em vez de 503.

  8. Os dois crons

    npm run news:fetch   # à hora, se houver NEWS_FEED_URL
npm run db:prune     # uma vez por dia

    A recolha de notícias corre fora da API de propósito: a página de entrada não deve ficar de pé ou no chão conforme o dia que o site de outra pessoa esteja a ter.

    O primeiro db:prune corre sem erro.

  9. O ensaio, contra o que acabou de ficar de pé

    npm run ensaiar --workspace @vicehub/api -- \
  --base=https://api.vicehub.com

    Cria conta, renova a sessão pelo cookie, funda uma crew e um servidor, abre um tópico, põe um anúncio, vê os ecrãs que isso produz — e depois apaga tudo o que criou, incluindo a própria conta.

    “ensaio limpo, e sem deixar nada para trás”. Um 401 na renovação diz que os domínios não são o mesmo sítio; um 500 no registo diz que o seed não correu.

  10. E o correio a sair

    Pedir uma recuperação de palavra-passe para um email teu e abrir o que chegar. O link tem de começar pelo APP_PUBLIC_URL — se apontar para localhost, quem o receber não vai a lado nenhum, e o pedido parece ter corrido bem na mesma.

    O link abre a página de recuperar no domínio certo.

Depois, e só depois

O post do lançamento está escrito e por publicar, em docs/press/x-post-lancamento.md. Leva três avisos em cima: o domínio é um marcador de posição, os números dos testes envelhecem ao próximo merge, e o link vai sozinho numa linha — uma imagem anexada substitui o cartão que o sítio serve por uma fotografia que não leva link nenhum.

As quatro ferramentas que o CI não corre: varrer, sondar, medir, ensaiar — mais correio, que mostra o que sai pelo SMTP.
Os visados ficam no browser deste telemóvel, e em mais lado nenhum.
